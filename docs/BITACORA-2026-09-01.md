## 2. Spec 003 — US6: Venta mostrador sin OT · Fase 10 ✅

Canal comercial de salida de mercancía sin Orden de Trabajo: **Vendedor** crea una **Solicitud de
Despacho** con líneas → **Almacenista** la recibe, genera **Remisión de Entrega** con consecutivo →
**doble firma digital** (quien recibe, luego quien entrega) → al confirmar se generan los movimientos de
salida (`origen: despacho`, costeo FIFO). Las líneas que el almacén no tiene se marcan como **compra
externa**: proveedor + costo + motivo "No disponible en almacén", **sin tocar el inventario**. Al
confirmar la entrega se envía **copia del PDF de la remisión al correo del cliente**.

### Modelo de datos (7 migraciones nuevas)

| Tabla | Notas |
|---|---|
| `solicitudes_despacho` | `numero` `SD-#####`, `cliente_id`, `vendedor_id`, `sede` (sigla IATA de ciudad), `estado` (`borrador`/`solicitada`/`recibida`/`remisionada`/`entregada`/`anulada`), timestamps de transición, `anulada_por`/`motivo_anulacion` |
| `detalle_solicitud_despacho` | `origen` (`inventario`/`compra_externa`), `inventario_id` nullable, `descripcion`, `cantidad`, `costo_unitario`, `proveedor_externo`, `costo_compra_externa`, `motivo`, `movimiento_id` |
| `remisiones_entrega` | `numero` `REM-#####`, `solicitud_id` 1:1, `generada_por`, `entregado_por_nombre`, `recibido_por_nombre`/`_documento`, `firma` (recibe), `firma_entrega` (entrega), `nota_entrega`, `entregada_en`, `enviada_al_cliente_en` |
| ALTER `movimientos_inventario.origen` | +`despacho` |

### Código

- Modelos: `SolicitudDespacho`, `DetalleSolicitudDespacho`, `RemisionEntrega` (+ 3 factories).
- `app/Services/Inventario/ConsecutivoDespachoService.php` — `SD-#####` / `REM-#####` con `lockForUpdate()`.
- `app/Services/Inventario/DespachoService.php` — `crear` / `recibir` / `generarRemision` /
  `confirmarEntrega` / `anular`. `confirmarEntrega` es transaccional: valida stock por línea
  (`StockInsuficienteException` revierte todo), genera `MovimientoService::salida(origen: 'despacho', ...)`
  por línea de inventario, exige ambas firmas, y **fuera** de la transacción envía el correo al cliente
  (fallo de correo no revierte la entrega).
- `app/Policies/SolicitudDespachoPolicy.php` (registrada en `AuthServiceProvider`): crear/editar/anular →
  Vendedor+Admin; recibir/remisionar/entregar → Almacenista+Admin.
- `app/Mail/RemisionEntregada.php` + `resources/views/mail/remision-entregada.blade.php` (markdown + PDF adjunto).
- `app/Http/Controllers/RemisionEntregaController.php` + `resources/views/pdf/remision-entrega.blade.php`
  (dompdf `^3.1`). El PDF reproduce el formato físico "REMISIÓN {sede} Nº ####": **logo embebido**, datos
  del cliente (dirección, NIT, teléfono, correo de spec 000), **una sola tabla** de artículos
  (Cant./Referencia/Descripción, **sin costos**), nota de entrega, bloques Entrega/Recibe con ambas
  firmas. **No expone** la clasificación interna inventario/compra externa (es trazabilidad interna).
- UI Volt: `resources/views/livewire/despacho/{index,form,entrega}.blade.php`.
  - `form`: selector de Ciudad (sede) + cliente + repetidor de líneas con aviso de stock insuficiente y
    "Total estimado" en vivo; redirect `navigate: false` (evita perder el modo oscuro).
  - `entrega`: dos bloques rotulados ("Despachar de bodega" / "Compra externa"), chip "stock insuficiente"
    por línea, resumen de líneas; firmas **secuenciales** (aparece la de quien entrega tras firmar quien
    recibe); botón "Borrar y volver a firmar"; toasts vía `Notifies`.
  - `index`: badge de pendientes, columna Ciudad, chip "N ext." en filas con compra externa.
- `resources/views/partials/nav-items.blade.php`: ítem "Despachos" + badge rojo con el nº de solicitudes
  pendientes de gestionar (Almacenista/Administrador).
- `resources/views/components/layout.blade.php`: logo del sidebar/topbar agrandado.
- `config/despachos.php`: lista de `sedes` (IATA → ciudad) + `sede_por_defecto` (env `DESPACHO_SEDE`).
- Rutas: `/despachos`, `/despachos/nueva`, `/despachos/{solicitud}`, `/despachos/{solicitud}/remision`
  tras `role:Vendedor|Almacenista|Administrador`.

## 3. Spec 004 — Sueldo historizado, valor día y hoja de vida · Fase 7 ✅

El costeo de mano de obra propia pasa de "tarifa por hora" a **día**.

- `config/personal.php`: `dias_mes` => 30 (env `PERSONAL_DIAS_MES`).
- Migración `create_sueldos_tecnico_table`: histórico `sueldo` + `vigente_desde` + `registrado_por`.
- Migración `add_datos_laborales_to_tecnicos_table`: +`fecha_ingreso`, `cargo`, `tipo_contrato`
  (`termino_fijo`/`indefinido`/`prestacion_servicios`); **elimina `tarifa_hora`**.
- `app/Models/SueldoTecnico.php` (+ factory). `Tecnico`:
  - `sueldos()` (histórico, más reciente primero)
  - `sueldoVigente(?$fecha)` = fila con mayor `vigente_desde ≤ fecha`
  - `valorDia(?$fecha)` = `round(sueldoVigente / config('personal.dias_mes'), 2)`
  - accessors `sueldo_actual` / `valor_dia_actual`
  - `registrarSueldo($valor, $vigenteDesde, $por)` — inserta fila nueva solo si el valor difiere del
    vigente a esa fecha (nunca edita/borra el histórico).
- `resources/views/livewire/admin/usuarios/index.blade.php`:
  - "Ficha de técnico": quita "Tarifa por hora"; agrega Sueldo mensual + Vigente desde + valor día
    (calculado, solo lectura, `Moneda::cop`) + Fecha de ingreso + Cargo + Tipo de contrato.
  - `guardar()`: upsert de `Tecnico` con datos laborales + `registrarSueldo(...)` si el sueldo cambió.
  - **Hoja de vida** (FR-013): botón en filas de usuarios con rol Técnico → panel de **solo lectura**
    (especialidad, estado, sueldo actual, valor día, datos laborales, tabla del histórico de sueldos,
    aviso de que carga/desempeño llegan con spec 002). Sin pantalla ni menú aparte.
- Tests `tests/Feature/Personal/`: `TecnicoTest` actualizado (`tarifaHora`→sueldo/valor día) +
  `SueldoTecnicoTest` (histórico, valor día, divisor configurable, no duplica fila) + `HojaVidaTest`
  (panel visible solo para técnicos, muestra histórico).

### Regla clave (FR-011)

Una OT **cerrada** se costea con el sueldo vigente a su **fecha de cierre**; las OT abiertas/nuevas usan el
sueldo actual. Subir el sueldo mañana **no recalcula** OT viejas. El contrato `Tecnico::valorDia($fecha)`
queda listo y probado para que spec 002 lo consuma.
